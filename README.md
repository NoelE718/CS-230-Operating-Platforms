# CS-230-Operating-Platforms

1. Briefly summarize The Gaming Room client and their software requirements. Who was the client? What type of software did they want you to design?
-  The client is The Gaming Room, a company that wants to expand its game that is called Draw It or Lose It, beyond Android devices. They wanted a web-based game that could work on different operating systems including Windows, Mac, Linux, and mobile devices. The game needs to allow multiple teams and players to participate, use unique names and IDs to help prevent confusion, and include timed rounds which makes the players feel pressure on answering a drawing since they are being timed. The goal was to create a user-friendly game that can be accessed across different devices while keeping the game information organized and secured.

2. What did you do particularly well in developing this documentation?
-  I was able to explain the clients requirements and connecting them to the software design very well and in detail. I was able to identify important features, such as unique team names, managing matches and players, and utilizing a single instance of the GameService class. I was also able to compare different operating systems and explain why Linux would be the better choice for hosting the game. My recommendations for memory management, storage, and security helped show how the game could work efficiently as more players started using it.

3. What about the process of working through a design document did you find helpful when developing the code?
-  Working through the design document has helped me understand how the different parts of the program were supposed to work together before I started the coding portion. The UML class diagram was especially helpful since it showed the relationships between Game, Team, Player, and GameService classes. It also helped me understand how inheritance and singleton pattern could be used in the application. Having a plan made it easier to organize the code, identify what each class was responsible for and avoid making unnecesssary changes later.

4. If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
-  If I could revise a part of my document, I would go back and improve the system architecture section by adding a more detailed diagram showing how the clients, server, REST API, database, and image storage communicate with each other. This would make it easier to understand how the game would work across different platforms. I would also explain more about how the system could handle a larger number of players and recover from connection problems, these changes would make my design clearer and provide a better guide for developing the actual application.

5. How did you interpret the user’s needs and implement them into your software design? Why is it so important to consider the user’s needs when designing?
-  I interpreted the client's needs by focusing on making Draw It or Lose It accessible across multiple platforms while keeping the game organized and user friendly. I recommend a web-based client server design so players could access the game through a browser instead of needing a separate application for every operating system. I also included unique identifier for Games, Teams, and Players, along with a single GameService instance to help manage the game's objects. Another recommendation for secure connections, database storage, and memory management were intended to keep the application reliable as it grows. Considering the user's needs is important because the software should solve the client's problems and provide a good experience for the people that are using it. If those needs are ignored, the appliation might not have the features users expect or might not work well on their devices.

6. How did you approach designing software? What techniques or strategies would you use in the future to analyze and design a similar software application?
-  My approach to designing software was to start identifying the client's requirements and then break the project into smaller parts to make it easier to manage. I used a UML diagram to understand how the classes would relate to each other and consider different operating systems before choosing a recommended architecture. I also looked at memory management, storage, security, and network communication to understand what the application would need to work properly. In the future, I would like to continue using techniques like requirements analysis, UML diagrams, and object-oriented design. i would also create prototypes and test important features early in development which will help me find problems sooner and allows me the chance at making changes before they become a bigger issue and make the final product meet the client's expectations.
